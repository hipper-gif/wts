# ADR-0010 監査ログを点検専用から全レコード種別の汎用表にする

- 状態: accepted（2026-10-26）
- 決めた人: 杉原氏（「このまましてしまって」）
- 関連: Issue #78（監査ログが記録されない）・#79（入庫の外部キー違反が一般エラーになる）・sql/026

## 背景
`logAudit()` は入庫・出庫・乗車記録・点呼・車両・現金など全種別を `inspection_audit_logs` に入れるが、`inspection_id` が `daily_inspections(id)` への外部キーだったため、点検以外は id が偶然一致した時しか記録されず、失敗は try/catch で握りつぶされていた。Smiley テナントで 2026-04-16〜10-26 に 1,111 回失敗し、入庫・出庫・乗車記録の履歴は一度も残っていなかった。`ON DELETE CASCADE` のため点検を消すと同じ id の他種別の履歴も消える構造でもあった。

## 決定
1. 外部キー `fk_audit_inspection` を外し、`record_type` 列（種別）を足す。`inspection_id` の列名は読み手を壊さないよう残し「record_type の表の id」と読み替える。
2. `logAudit()` は常に `record_type` を書く。`field_changed` の意味（明細なし＝種別／明細あり＝項目名）は変えない。
3. 既存行は `field_changed` から種別を復元する（明細付き編集で項目名しか無い行は確定できるものだけ）。
4. 点検画面の履歴は `record_type='inspection'`（旧行は NULL）に絞る＝同じ id の入庫履歴が点検に混ざらない。
5. 入庫登録は、送信された出庫 id が存在しなければ入力エラー（画面を開き直す案内）として返す。外部キー違反を一般エラーにしない。
6. 全テナントに同じ migration を適用する（`sql/run_migration.php`）。新テナントは `tenant_base/000_schema.sql` が同じ形。

## 却下した案
- 種別ごとの監査表に分ける: 読み手が増える割に、今の列で足りる。
- 外部キーを残して種別ごとの表を参照する: MySQL の外部キーは1表しか指せない。

## 見張り
- `wts_php_error.log` の「監査ログ記録エラー」が適用後に増えないこと（clio `server_log.py wts`）。増えたら握りつぶしをやめて件数を朝に出す。
